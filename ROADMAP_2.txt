===============================
FULL PRODUCTION CODING PLATFORM
(ALGOFORGE ARCHITECTURE)
===============================

1) OVERALL ARCHITECTURE FLOW

Client (React + Monaco Editor)
        ↓
Backend API (Node + Express)
        ↓
Submission Service
        ↓
Queue System (Redis + BullMQ)
        ↓
Worker Service
        ↓
Docker Sandbox Container
        ↓
Judge Engine
        ↓
Database (MongoDB)


--------------------------------------------------

2) WHY THIS ARCHITECTURE?

• Thousands of users can click Run / Submit at same time
• Backend must not execute code directly (unsafe + blocking)
• Queue provides:
    - Concurrency control
    - Retry mechanism
    - Rate limiting
    - Priority execution
• Workers allow horizontal scaling
• Docker provides secure isolated execution
• Judge system validates outputs


--------------------------------------------------

3) MAIN SERVICES

A) FRONTEND SERVICE

Technology:
• React
• Monaco Editor
• Tailwind CSS
• Axios

Responsibilities:
• Show problem list
• Problem solving page
• Code editor
• Run button
• Submit button
• Custom input box
• Show testcase results
• Show submission history


--------------------------------------------------

B) BACKEND API SERVICE

Technology:
• Node.js
• Express
• MongoDB
• JWT Authentication

Responsibilities:
• User authentication
• Fetch problems
• Create submission
• Push job to queue
• Return submission status


--------------------------------------------------

C) QUEUE SERVICE (VERY IMPORTANT)

Technology:
• Redis
• BullMQ

Responsibilities:
• Store submission jobs
• Manage execution order
• Retry failed jobs
• Handle high traffic
• Prevent backend overload


--------------------------------------------------

D) WORKER SERVICE

Separate Node process.

Responsibilities:
• Pick job from queue
• Run docker sandbox
• Execute testcases one by one
• Compare output
• Generate verdict
• Save result in database


--------------------------------------------------

E) DOCKER SANDBOX ENGINE

Each submission runs inside:

• New isolated container
• Limited CPU and memory
• No internet access
• Read-only filesystem
• Auto container destroy after execution

Security flags example:

docker run --rm \
--memory=150m \
--cpus=0.5 \
--network=none \
--pids-limit=64 \
--read-only


--------------------------------------------------

4) EXECUTION FLOW

A) RUN CODE (Quick Execution)

User clicks Run
→ Frontend sends code to backend
→ Backend runs quick docker sandbox
→ Output returned immediately
→ No database storage


--------------------------------------------------

B) SUBMIT CODE (Judge Execution)

User clicks Submit
→ Backend creates submission entry
→ Status = QUEUED
→ Job pushed to Redis queue
→ Worker picks job
→ Runs docker container for each testcase
→ Judge compares expected vs actual output
→ Verdict generated (AC / WA / TLE / RE)
→ Result saved in database
→ Frontend polls submission status
